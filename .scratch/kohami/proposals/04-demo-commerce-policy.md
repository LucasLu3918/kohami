# 全流程 mock 展示階段政策 v0.2

日期：2026-10-13｜方向：ACCEPTED｜詳規：本輪工程整理，供審閱｜產品驗收：NOT_EXECUTED

## 1. 適用範圍與決策來源

使用者要求繼續完善政策：實際運費與退款人員先規劃機制；物流不串接，以 mock 示意；退款依管理者權限判斷、點選並顯示相應狀態。其後明確確認「金流、退款、發票都先 mock」。

適配性：適合目前本地開發與展示，可先驗證購物及管理旅程，避免供應商資格阻擋。mock 能證明應用行為，不能證明真實付款、配送、退回、稅務處理或正式營運能力。

本文件優先適用於目前 mock 階段；取代政策 01–03 中「所有退款須不同人提案／Owner 核准」、本階段必須真實供應商資格／契約才可開發的要求。其他已採用規則保留。原雙人政策屬歷史基準；正式資金操作採單人或雙人，須在真實金流啟用前另確認，不自動沿用任何一種。

技術維持 ASP.NET Core／.NET 10、Vue 3／Nuxt SSR、Microsoft SQL Server。mock 僅替代外部服務；後續應用仍需實作真實的伺服器授權、交易快照、資料持久化與競爭控制。既有純 C# 實驗與 SQL 開發 smoke 不是本文件全部驗收證據。

## 2. 模式、資料與共用規則

- 本階段唯一可用商務模式為 `mock`。付款、退款、配送、憑證記錄均攜帶模式及資料集識別，畫面和下載檔明示「展示環境，無實際交易」。退款用「模擬退款完成」，不稱「款項已入帳」。
- 不接收真實卡號／CVV／銀行帳號，不寄真實包裹、不呼叫供應商、不開正式發票；不放承運商正式追蹤連結或有效格式的發票號碼。憑證識別使用 `DEMO-` 前綴。
- 商品、庫存、收件地址與訂單範例使用可重建的合成資料；測試帳號不填真實電話地址。示意照片／插畫仍須有合法展示權利，不因 mock 而豁免授權。
- mock 狀態只能由受控後端 adapter／授權測試情境產生；前台返回頁、URL 查詢參數、localStorage 或按鈕不能直接把訂單標已付款／已退款。測試情境操控入口僅供獲授權管理者，不是顧客 API。
- 金額沿用 TWD 整元、優惠一次捨入／精確分攤、單一優惠碼、不可變 Price Snapshot；零元訂單及門檻免運仍不啟用。
- 每筆操作具唯一操作識別與版本。相同內容重送回傳同一結果；識別相同而內容不同拒絕。交易、額度保留、狀態及稽核須一致寫入，不用停用按鈕代替後端冪等。
- 後續正式模式須獨立設定、資料集及 credentials，不以 UI 開關轉換。mock 已付款／已送達／已退款記錄不能升格成真實交易；切換須新建資料集、驗證資格／契約並另經啟用確認。
- 本地或受限展示預設禁止索引（noindex），保留 Nuxt SSR／三語 HTML、canonical／hreflang 的技術驗收；不把假商品與示意政策送正式 sitemap 或當作真實商店發布。

## 3. 模擬付款與庫存

付款狀態與訂單狀態分開：待付款、模擬付款處理中、待確認、模擬付款成功、付款拒絕。後端提供可重現的成功、明確拒絕、結果未知、重複／亂序、金額或幣別不符、晚到成功情境。

- 首次結帳建立 15 分鐘 Reservation；重送不展延，不重複保留。SQL 最後一件併發購買只能有一筆成功承諾，失敗不留下部分保留。
- 只有同一資料集、訂單、Payment Attempt、幣別與應付金額相符的後端結果才能確認付款；金額不符留異常並禁止出貨。
- 待確認不是失敗，不要求顧客重付；保留期限仍按既定時計到期。查核只能更新同一嘗試，不任意新增可能重複的有效交易。
- 到期／取消釋放一次庫存；之後成功進入補償待處理，禁止恢復原訂單／重新占用庫存，建立包含原運費的全額模擬退款案件。
- 成功後舊拒絕／處理中事件不降級結果；同一事件重送不多扣庫存、不產生第二張有效訂單。重複有效收款事件須進異常核對，不忽略可能的額外交易。
- mock 對帳核對模擬交易台帳、訂單、庫存承諾、退款與補償；留待處理原因及處置紀錄，不聲稱已與銀行對帳。

## 4. 運費、配送與取消

運費金額先不定案。機制採版本化固定費用表：方式、支援區域、TWD 金額、生效範圍、啟停與版本；mock 測試資料可帶合成金額，但須標「示意運費」，不得當成費率推薦或正式報價。

- 先提供「模擬宅配」及「模擬超商取貨」等中性方式，不宣稱任何品牌已簽約。區域可用合成本島／不支援地址測試；真實地址排除表延期。
- 結帳展示商品小計、優惠、示意運費、總額及模式，保存費用表版本；缺少有效費用、地址不支援或負值時阻止確認，保留購物車，不暗中採 0 元。
- 新費用表不覆寫歷史訂單；購物車報價失效重新報價並請顧客確認，不能直接多扣款。
- 配送狀態：待模擬出貨 → 模擬已出貨 → 模擬配送中 → 模擬已送達；配送中可轉模擬配送異常，異常可恢復配送中或模擬退回。所有操作保留版本與歷程；不合法／舊版轉移拒絕，重送回同一結果。已送達後不被舊配送中事件回退。
- Owner 或被授履約案件範圍的 Customer Support 可推進狀態；付款待確認／拒絕、取消、待補償訂單均不能模擬出貨。頁面無真實到貨承諾。
- 模擬交承運前可取消；模擬出貨與取消併發由同一訂單版本裁決，不能同時出貨且取消。出貨後轉退貨案件。取消與退款分開：已模擬付款的取消生成待管理者處理退款，不因取消即宣告退錢。
- 2–3 營業日出貨與客服目標只保留為日後規劃；mock 時間不能當作 SLA 達標證據。

## 5. 單一管理者退款與售後

「管理者」預設映射既有 Owner，不新增第五個最高角色。Customer Support 可受理／提出案件，Merchandiser／Analyst 不可退款；被授權 Owner 可直接處理，不要求另指定第二人或退款代理。未授予退款權限的管理帳號仍不能操作。

### 操作與狀態

| 狀態 | 管理端行為 | 顧客顯示 |
| --- | --- | --- |
| 待管理者處理 | 受理顧客申請／取消／補償案件；Owner 查看原單、金額、原因與歷程 | 退款申請待處理 |
| 模擬退款處理中 | Owner 點選退款並確認；後端通過條件後保留可退額、建立唯一退款操作 | 模擬退款處理中，無實際資金移動 |
| 模擬退款完成 | adapter 的明確成功結果才成立；部分／全額分別彙總 | 已模擬退款 TWD X；無實際退款入帳 |
| 模擬退款失敗 | 已確認未執行才釋放該筆額度；Owner 可對同一案件發起新操作 | 模擬退款失敗，待管理者處理 |
| 模擬退款待確認 | 逾時／結果不明保留額度，查詢同一操作；禁止再建一筆 | 模擬退款結果待確認 |
| 申請未核可／撤回 | 未執行案件才可轉移；拒絕須理由並留客服入口 | 顯示原因與聯繫方式，不把技術異常當拒絕理由 |

按鈕能否顯示僅供 UX；伺服器每次查核登入、有效 Owner 退款權限、後台 MFA、案件範圍及版本。退款確認頁帶訂單、可退額與原因；不讓前台自行傳入核准者或最後狀態。沿用後台敏感操作近期重新驗證、最低權限與受保護稽核。

### 金額、競爭與庫存

- 可退額 = 本筆已確認的模擬實收 − 已完成退款 − 其他處理中／待確認退款的保留額。同一有效操作自己的額度不二次扣除；原付款未知不得普通退款，先完成付款查核。
- 全額取消／晚到成功補償含原已收示意運費；部分退貨依原快照的商品實付分攤，不追補原免運；原運費只能退一次。商品退回數量與已退款數量須核對，不以任意輸入金額繞過明細上限。
- 伺服器須拒絕零／負額、超額、已退款品項、篡改幣別／原交易、跨會員案件及舊版本。並行退款須原子保留額度，總完成額與未決保留合計不超實收。
- 多按、刷新、網路重送及重複成功事件不產生第二筆退款；待確認事件只能查核同一操作。終態失敗才可釋放；未知不視為失敗。
- 退款完成不直接將取消／退貨訂單恢復為可出貨，也不自動增加可銷售庫存。未付款取消／到期只釋放有效 Reservation 一次；已付款且未模擬交承運的取消，若付款已將保留轉為交易扣減，須以唯一反向庫存異動回補原扣減，不能同時釋放保留及再次回補。取消與出貨以同一交易／版本裁決；無法確認未出貨或原庫存異動時列例外，不盲目回補。已出貨退回商品須獨立模擬 Inspection，合格後以唯一庫存調整記錄入庫。晚到成功仍不恢復已取消／到期訂單。
- 拒絕理由、退款結果與模擬憑證調整分開。既有正式消保／資料權利基線維持，mock 不改寫其法定期限；正式條款與處理能力啟用前審查。

### 人員與代理機制

先規劃具名帳號、角色、退款權限、授權起迄、案件指派、撤銷與稽核；不填造真人或要求本階段兩人。展示可用合成 Owner／Support 帳號驗證正反向權限。未指定代理時顯示無代理，不建立共享管理帳號。撤權後既有登入及尚未送出的佇列操作須重新判斷權限，禁止再發起未授權退款；已發起的操作仍由受控系統接收／查詢可信結果並完成對帳，不能因操作者撤權就遺失結果、釋放未知額度或停止追蹤。系統結果處理不授權該操作者再發新退款。

## 6. 模擬憑證、客服與通知

- 付款確認後建立「模擬交易憑證」，明示無稅務效力；僅測試訂單及金額關聯。不蒐集真實載具／統編，不稱已向財政部開立。
- 未付款取消不產生已付款憑證；付款後退款建立原憑證的模擬調整紀錄，部分／全額金額可追溯。展示「模擬調整完成／失敗／待確認」，不把模擬作廢／折讓宣稱合法稅務處理。
- 憑證失敗不回滾已完成退款，不阻擋顧客查閱退款；重試同一調整不能多建有效憑證。退款及憑證狀態分列，全部必要項完成才結案。
- 訪客及會員只查自己的案件／憑證；不以可猜的 `DEMO-` 識別作授權。保留訪客單筆短效驗證及會員所有權規則。
- 本階段通知用隔離的測試收件匣／站內事件記錄，不寄真實 Email／簡訊；內容明示模擬。收件匣依測試帳號授權，復原／驗證碼不出現在公開頁或通用日誌。登入驗證使用測試投遞 adapter，不降低既有驗證要求。
- 一般客服、退貨受理、驗收、退款、補償分開呈現；失敗與待確認留處理入口。直接換貨／額外無理由退貨期未採用，本階段不新增承諾。
- 保留既有資料最小化、保存／刪除及稽核政策；重設 demo 只清指定合成資料集，不能擦除其他環境或真實使用者資料。

## 7. 換裝與其他未決政策的規劃

既有非 AI、無本人照片、三視圖、一次一件、自由選角色、明確選身形、商品尺碼獨立、主動收藏與版本失效政策維持。新增的工程整理情境：版本失效時停止重現；替代版本須使用者重新選擇；授權撤銷立即停止受影響展示／匯出，商品本身依獨立上架條件判斷；照片／尺寸表備援不中斷購物。

收藏數量仍 PROVISIONAL。**建議待票 27 的素材實證後，再審閱最多 20 組、滿額時由本人刪除／覆寫而不自動刪舊收藏的方案**；本輪未採用此上限。實際支援尺寸、SKU 清單、素材製作／下載權利不由 mock 推定。品牌、商家資料、正式售價／運費、成本與法定保留分類仍列正式啟用待辦，不阻擋合成資料的政策整理。

## 9. 票券與正式啟用邊界

保留 38 張票及編號。本輪新增詳規不等於產品完成；01–03 只維持政策票 resolved，06 仍 claimed，其他票不改完成狀態。

04／05 的本階段驗收改為 mock adapter 契約與情境實證；服務商選型、資格、費用及真實沙盒移至各票「正式串接延期清單」。04／05 仍須實作與驗證 mock 契約後才 resolved，不因本文件存在就解鎖其產品依賴。

13–15、18–22、25–26 依本階段 mock 契約驗收。26 是「可審閱的 mock 核心商店交付」，不是可正式收款營運。38 留待正式營運後取得真實 SLA 紀錄，不把它當作 mock 交付前置條件。

真實串接前至少確認：供應商與商家資格／契約、真實費用表、資金退款授權制度、具名人員與代理、通知渠道、實際憑證規則與法定資料分類、可信事件與對帳、併發／重啟／復原演練、正式條款與部署。這是延期清單，不是已完成或本輪新增實作任務。
