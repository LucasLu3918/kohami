# 06: 確認商店技術方案與品質基準

**What to build:** 以最小實證確認前台、商務核心、儲存與部署方案，訂定品質檢查、資源與成本估算，讓後續旅程可在明確技術邊界內交付。

**Blocked by:** 01：確認結帳與庫存交易規則；03：確認身份、權限與資料政策

**Status:** ready-for-agent

**Framework decision:** accepted（ASP.NET Core／.NET、Vue.js、Microsoft SQL Server）

**Work status:** claimed（有界實證；尚未完成）

- [ ] 比較候選方案對三語可索引內容、交易／庫存不變條件、身份權限、金物流擴充及維護的支援，以有界實證記錄能力與限制。
- [ ] 取得重大語言、平台、資料儲存與部署決策確認；邏輯領域所有權不自動變成微服務，具體 API／Schema 隨旅程建立。
- [ ] 定義瀏覽器旅程、外部供應商沙盒、公開交易並行、復原與人工素材審核的檢查方式，包含驗證命令或待完成條件。
- [ ] 建立效能、可及性、可靠性、安全與復原的量測矩陣；區分規劃目標、待確認門檻與已測證據。
- [ ] 提出開發、服務、維護及負載情境成本／人力估算與信心限制，不把 NT$8,000／月視為已證實總預算，不轉撥停用的 AI 預算。

- 階段：前置決策與實證。
- 驗收對應：V06、V11；N01、N03–N04；User Stories 6–7、82–85、87。

- 先確認阻擋票均已完成；`ready-for-agent` 不解除依賴或重大待決條件。前置票須提供可審查證據並完成必要決策確認，不能把 UNKNOWN 或 PROVISIONAL 改寫成既定事實。
- 本票有實作時，按確認旅程補齊必要資料、介面、畫面、權限與錯誤行為，再驗證輸入、輸出、資料、事件及消費者影響；不拆成單獨的 schema／API／UI 層票。

- 票單採用僅批准本機議題建立；後續工作依當次授權與必要決策執行。實作、付費／採購、素材製作、正式部署收款及換裝啟用不得僅由票單狀態推定授權；Phase 3／4 另案處理。
