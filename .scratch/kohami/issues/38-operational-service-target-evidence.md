# 38: 以實際營運紀錄驗證服務目標

**What to build:** 取得營運啟用批准後，追蹤月可用性、出貨／客服時效、每日對帳、季度復原及實際成本；資料不足不宣稱達標，也不自動擴充 Phase 3／4。

**Blocked by:** 26：核心商店獨立交付與啟用審查

**Status:** ready-for-agent

- [ ] 僅在取得獨立營運啟用批准並完成啟用後收集已確認用途的最小必要紀錄；本票完成前置工作不等於已正式營運。
- [ ] 按確認監測口徑與完整量測期評估核心商務每月 99.9% 規劃目標，樣本／期間不足保持未驗證。
- [ ] 依營業日及例外核對付款確認後約 2–3 營業日出貨、一般客服兩營業日與高風險付款一營業日首次回應目標，附實際紀錄與限制。
- [ ] 核對每日對帳、重大警示及初期至少每季復原演練的實際執行情形；未執行項目不填 PASS。
- [ ] 比較實際服務、人力與維護成本及估算，提出有證據的改善建議，不自動建立 Lookbook、轉換分析、國際擴充或其他 Phase 3／4 功能。
- [ ] 營運證據包含日期、範圍、版本、方法、結果、責任及限制，遵守資料保存政策，不長期保存原始提示、工具輸出或未授權個人資料。

- 階段：營運觀測。
- 驗收對應：N03–N07；V11–V12；User Stories 83–88。
- 基準：KOHAMI 核心商店與模特換裝參考規格 v0.1（含 Comments）、產品規劃書、術語表、現行決策 D396–D446、驗證計畫及 ADR-0001；遵循 Round 18，有效決策不等於歷史編號總數。
- 先確認阻擋票均已完成；`ready-for-agent` 不解除依賴或重大待決條件。前置票須提供可審查證據並完成必要決策確認，不能把 UNKNOWN 或 PROVISIONAL 改寫成既定事實。
- 本票有實作時，按確認旅程補齊必要資料、介面、畫面、權限與錯誤行為，再驗證輸入、輸出、資料、事件及消費者影響；不拆成單獨的 schema／API／UI 層票。
- 沿用已確認測試接縫：瀏覽器端到端旅程為主；付款事件、庫存競爭與復原另用必要外部邊界驗證；素材品質及權利保留人工審核。執行前均屬 NOT_EXECUTED，不以圖片載入或工具成功當成所有驗收通過。
- 票單採用僅批准本機議題建立；後續工作依當次授權與必要決策執行。實作、付費／採購、素材製作、正式部署收款及換裝啟用不得僅由票單狀態推定授權；Phase 3／4 另案處理。
