# 25: 商務監測、安全與災難復原

**What to build:** 驗證權限與秘密保護、去識別化日誌、交易警示，完成備份還原及金流對帳演練，提供 RPO／RTO 證據。

**Blocked by:** 21：交易憑證與退款發票處理；23：最小化報表與資料生命週期

**Status:** ready-for-agent

- [ ] 驗證後台 MFA、角色越權、可信金流、秘密掃描及日誌去識別化的正反向情境，未解決重大問題列為阻擋。
- [ ] 商務健康、關鍵交易及重大付款差異有監測、分級警示、負責人與處理程序，可由受控異常觸發驗證。
- [ ] 在授權且不破壞正式資料的環境完成災難備份還原及付款／退款／訂單對帳，量測 RPO ≤ 1 小時、RTO ≤ 8 小時並附條件與結果。
- [ ] 復原後核對庫存、歷史快照、履約及發票一致性；每日對帳與季度演練的排程／責任明確。
- [ ] 定義月可用性口徑但不將單次演練當成每月 99.9% 證據，保留恢復與回退操作指引。

- 階段：Phase 1 核心商店。
- 驗收對應：N03–N04、N07；V12；User Stories 79–84。

- 先確認阻擋票均已完成；`ready-for-agent` 不解除依賴或重大待決條件。前置票須提供可審查證據並完成必要決策確認，不能把 UNKNOWN 或 PROVISIONAL 改寫成既定事實。
- 本票有實作時，按確認旅程補齊必要資料、介面、畫面、權限與錯誤行為，再驗證輸入、輸出、資料、事件及消費者影響；不拆成單獨的 schema／API／UI 層票。
- 沿用已確認測試接縫：瀏覽器端到端旅程為主；付款事件、庫存競爭與復原另用必要外部邊界驗證；素材品質及權利保留人工審核。執行前均屬 NOT_EXECUTED，不以圖片載入或工具成功當成所有驗收通過。
- 票單採用僅批准本機議題建立；後續工作依當次授權與必要決策執行。實作、付費／採購、素材製作、正式部署收款及換裝啟用不得僅由票單狀態推定授權；Phase 3／4 另案處理。
