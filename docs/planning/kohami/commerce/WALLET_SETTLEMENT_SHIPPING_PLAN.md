# 會員儲值餘額扣抵、訂單履約與退貨退款規劃

日期：2026-10-14｜狀態：**READY_FOR_REVIEW／規劃提案**｜未授權產品實作或正式收取儲值

## 本次已確認的增量範圍（2026-10-15）

使用者已選「核心商店本機版→會員實付儲值本機版→換裝另版→正式營運」。會員儲值第一輪只驗實付餘額；贈送金保留分帳方向，但暫不發放、不參與扣抵，不對外顯示為可用額度。

原文實付／贈送混用及活動到期相關內容保留作 [member-wallet/06](../../../issues/member-wallet/06-promotional-credit-policy-and-enablement.md)的延後選配，不是首輪實付版的必要完成項；對相關驗收標 DEFERRED（未啟用），不能把未測贈送金算 PASS。原本只以 W0–W4 描述的工作改由 member-wallet/01–05 逐票執行，順序唯一來源為 [執行主計畫](../delivery/IMPLEMENTATION_PLAN.md)，不另維護第二份進度。

首輪仍全合成入金與退款，不發生實際資金。正式入金、退款去向與資金作業覆核均保留決策，於主計畫提供至少兩方案及建議，未決不實作受影響正式能力。

## 1. 決策基準與適配性

使用者已選定單一商店閉環：只有 KOHAMI 會員可用餘額購買 KOHAMI 商品；餘額不得轉讓或提領；實付儲值與贈送購物金分帳。結帳以資料庫中已確認的會員餘額扣抵作為訂單付款依據，配送由有權限的後台人員更新狀態。信用卡與第三方支付列為未來選配。

此方案適合單一品牌商店的會員回購，並符合 Commerce 持有訂單、付款、退款及庫存一致性的模組化單體。會員餘額、退款與對帳具經濟價值，安全與可靠性高於一般 CRUD。本文件是 M0 mock 之後的候選方向，不改變目前全 mock 政策、已批准 M0 範圍或任何 NOT_EXECUTED 驗收，也不批准建立真實儲值、資料庫 schema/API、供應商合約或正式上線。

### 建議名稱

- 面向會員：**會員儲值餘額**；分列**實付儲值餘額**、**贈送購物金**。
- 結帳操作：**以會員儲值餘額扣抵**。不要用「資料庫扣款」作產品文案；資料庫扣帳是內部記錄，外部收款是另一筆入金流程。
- 訂單顯示：**訂單成立、備貨中、訂單完成、訂單取消**；配送、退貨及退款各自顯示狀態，不塞進一個「訂單狀態」欄位。

「會員儲值餘額」是產品用語，並非法律分類結論。單一商店、不可轉讓及不可提領可作為範圍條件，但不能單憑這些條件推定免受電子支付、商品／服務禮券、預付交易或消費者保護規範。法規分類、履約保障、退款條款及實付餘額是否可返還，列為真實收款前的阻擋決策。[電子支付機構管理條例](https://law.moj.gov.tw/LawClass/LawAll.aspx?PCode=G0380237)第 3、4、5 條涉及多用途支付、收受儲值款項及業務許可；第 3 條列有只向發行人指定者兌換之商品／服務禮券例外，是否適用須由法務依實際契約與營運判斷。[消費者保護法](https://law.moj.gov.tw/LawClass/LawAll.aspx?PCode=J0170001)第 17、18、19、19-2 條涉及特定行業定型化契約、通訊交易資訊、解除權與返還對價；另須核對[商品（服務）禮券定型化契約事項](https://www.ey.gov.tw/Page/DFB720D019CCCB0A/5486b053-67e1-47e8-90e4-a9a59529dc87)及預付型交易指引。以上是規劃風險提示，不是法律意見或合規結論。

## 2. 執行順序與範圍

順序與明確票券只維護於 [執行主計畫](../delivery/IMPLEMENTATION_PLAN.md)。member-wallet/01–05 交付合成實付餘額閉環；member-wallet/06 是停用中的贈送金選配。正式入金、適用性審查、資金覆核與退款去向由 production-launch/01 在正式收款前把關，不再用舊 W0–W4 表同時描述展示與正式營運。

信用卡／第三方支付維持未採用選配，不是本輪實付版前置；本機只用合成入金，正式版必須先有明確、可信且可對帳的入金來源及相應批准，不允許直接編輯餘額。

## 3. 會員餘額與帳本規則

1. 會員必須登入並通過後端會員所有權檢查才能使用餘額；訪客仍可瀏覽、選商品及暫存購物車，但此規劃下的結帳前須登入。相同 Email 不自動合併帳戶或購物車。
2. 每個幣別、會員及餘額來源分開記錄。至少區分實付儲值與贈送購物金，不互相混算、不跨會員轉移、不兌現或提領；多幣別目前不在範圍。
3. 以不可變更的帳本分錄記錄入金確認、扣抵、退款、贈送、到期（若未來合法採用）、沖正及受控更正。餘額快取／投影只供讀取，不能取代帳本；禁止管理者直接 UPDATE 餘額。錯誤以有原因、操作者與來源關聯的反向分錄更正。
4. 實付入金只有在外部款項已實際收到且通過唯一來源核對後，才能從待確認轉成可用。付款通知、瀏覽器返回、管理員畫面或單一資料庫欄位都不是入金證據。重複通知以同一入金識別重播，不重複增額；同識別不同金額／幣別／會員列待調查。
5. 贈送金由核准活動規則產生，保留活動、期限（若採用）、適用商品／訂單與來源。不得把贈送金記成實收。本輪不發放也不使用贈送金；活動期限、消耗順序、運費及退貨恢復等規則，在 member-wallet/06 另案採用前維持 DEFERRED。
6. 帳本分錄包含唯一交易識別、會員、來源 bucket、正負方向、TWD 金額、原因碼、關聯訂單／入金／退款、操作者或系統來源、建立時間、冪等鍵與前後版本。禁止負餘額；會員與管理後台不可刪改已確認分錄。
7. 對帳須比較已確認入金、錢包負債餘額、扣抵訂單、退款／沖正及外部入金來源；不一致時停止相關入帳／退款或標示待處理，不能以總額調平掩蓋來源差異。

贈送金消耗順序、有效期限、到期通知、失效後退貨退款處置尚未由使用者決定。安全預設是分帳、保留逐筆來源、不宣告贈送金可兌現；實作前仍需產品／法務決策，不由工程自行填造期限。

## 4. 結帳、扣抵與訂單建立

建議 Commerce 在同一 SQL transaction 重新驗證登入會員、商品／SKU／價格快照、優惠、可售庫存、應付 TWD、錢包來源分配與可用餘額；原子寫入訂單與不可變快照、庫存異動、帳本扣抵、冪等結果、稽核及 outbox。任何條件失敗全部 rollback；錢包不足時不成立訂單、不扣餘額、不承諾庫存，回到加值或調整購物車流程。

同一冪等鍵與相同請求只回傳原結果；相同鍵不同請求拒絕。並行購買採資料庫交易／鎖或條件更新裁決，避免重複扣抵、超賣與負餘額。commit 回應遺失時以原冪等鍵查原訂單與帳本，不重扣。Order、WalletLedger、InventoryMovement 與 Outbox 必須同交易提交，禁止以非同步事件拆開而留下已扣餘額卻沒有訂單，或有訂單卻未扣款。

此規劃下的訂單成立表示錢包扣抵已入帳；若餘額不足或資料庫不可用，不得顯示「訂單成立」。後續信用卡／第三方支付若另行採用，需增加支付授權／capture／未知結果及多來源分攤，不可直接沿用本地扣抵等同即時結清的假設。

## 5. 訂單、配送、退貨與退款狀態

| 概念 | 建議狀態 | 規則 |
| --- | --- | --- |
| 訂單 Order | 訂單成立 → 備貨中 → 訂單完成；可在交承運前取消 | 「完成」是訂單履約摘要，不代表退貨權利消失。已交運後不可直接取消，改建退貨／攔截案件。 |
| 配送 Shipment | 待出貨 → 已交運 → 配送中 → 已送達；可進配送異常、退回寄件人 | 每次變更記操作者、時間、原因、版本及可用佐證／物流單號；管理員輸入代表本店紀錄，不是承運商即時證明。 |
| 退貨 Return | 申請中 → 已受理／已拒絕 → 退回運送中 → 已收件 → 檢查中 → 已結案 | 退貨申請、收到商品、驗收、可再售入庫及退款是不同結果；拒絕須有原因及客服入口。 |
| 退款 Refund | 申請中 → 處理中 → 已退款／退款失敗／結果待確認 | 只有實際退款分錄與來源處理成功後才能顯示「已退款」。未知維持待確認並查同一操作，不可重複退。 |

顧客頁可將各狀態組合呈現，例如「訂單成立・配送中・退貨申請中・部分退款」，但後端不可只有一個狀態欄位。已送達後何時由後台或顧客確認為「訂單完成」仍需營運決策；不得用訂單完成狀態縮短法定解除／退款權利期限。

### 取消、退貨、退款與庫存

- 交承運前取消：鎖定 Order 版本，停止後續出貨；反向帳本分錄退回原扣抵來源，庫存以唯一 Movement 回補。若已部分出貨或來源狀態不明，建立例外案件，禁止直接回補。
- 交運後退貨：依受理及收件資料逐件驗收。可再售與隔離數量分列；只有通過驗收後以唯一 Movement 入庫，不因退款成功自動增加可售庫存。
- 退款金額依原訂單快照、退回數量、優惠分攤、運費資格與各筆未決退款計算；部分退款／全額退款分開，完成額加未決保留額不得超出原可退金額。訂單顯示「已退款」僅限全額退款結案；部分退款應顯示金額與剩餘案件。
- 錢包付款的退款去向按原扣抵來源及法規／條款確定。不得將贈送購物金當成實付退款；混合付款（未來選配）須以原付款來源分攤並保留順序。是否可退回實付儲值、是否可要求原支付方式、贈送金在退貨後的恢復規則均須法務及產品確認，不以技術預設限制法定權利。
- 未來信用卡／第三方支付若與錢包混合付款，需保存各來源本次實付分攤；退款按核准政策及法令退還原來源或使用者依法可選的目的地，未知外部結果保留額度與狀態。

## 6. 管理後台履約操作

- 將「標示配送」稱為**人工履約紀錄**。後台由具 `fulfillment.update` 權限的角色，只能執行合法狀態轉移；不能直接任意指定已送達／完成、改寫歷程或操作其他會員訂單。
- 每筆狀態變更記錄 actor、伺服器 UTC 時間、前後狀態、原因、Order／Shipment 版本及來源註記。追蹤碼或交寄佐證依必要性與個資最小化原則保存；介面清楚區分「店家已更新」與「物流商已回報」。
- 發貨與取消共用同一 Order 競爭控制；已取消、扣抵未知、退款處理中的訂單不得出貨。重送相同 idempotency key 回傳原狀態；舊版本與不合法轉移拒絕並留下稽核。
- `fulfillment.update` 與 `refund.execute`、`wallet.topup.reconcile`、`wallet.adjust` 分權。後台不能以編輯訂單狀態直接產生退款或餘額；人工入金核對與餘額更正需更強的審核／覆核、稽核及每日例外報表，具體單人／雙人規則仍待資金作業決策。

## 7. API、資料與安全規劃

領域責任建議：Commerce 持有 Wallet、Checkout、Order、Ledger、Refund 及 InventoryMovement 的交易裁決；Fulfillment 持有 Shipment、Return、Inspection 與履約命令，透過 host 協調原子庫存意圖；CustomerCare 僅建立／管理案件，不可直接改錢包或退款終態。沿用模組化單體；本文件不新增獨立部署或微服務。


帳本、入金證據及退款資料是高價值資產。未來啟用應將安全維度提升到 Q3 級別並完成 SAL 分級及獨立安全審查，覆蓋重放／重複入金、雙花、競爭扣抵、跨會員物件存取、管理者濫權、資料庫人工改數、退款超額、稽核竄改、備份還原後重複入帳、日誌洩露敏感資料與營運中斷。Owner 依有效權限／scope與最低權限政策驗收。

需要稽核的待辦包含入金外部對帳差異、帳本負債不平、Unknown 扣抵／退款、手動配送更正、拒絕的越權操作、重播衝突與復原演練結果。日誌不記錄密碼、秘密、完整支付憑證或不必要的地址資料。備份／還原需確認錢包餘額投影可由帳本重建，且對外部入金／退款逐筆對帳。

## 9. 實作前待決與批准閘門

1. 法律分類、商品／服務禮券或其他預付交易規範、履約保障、營業主體與對消費者揭露條款。
2. 實付入金方式、可信入金證據、商家帳戶對帳來源、錯款／溢款處理及入帳操作覆核。
3. 贈送金的使用順序、適用品項、有效期、通知、退貨與取消時的恢復／失效規則。
4. 訂單「完成」的明確條件、人工配送證據要求、配送異常處理與真實客服 SLA。
5. 退貨資格、依法應退金額／期限、退款去向、運費與原付款來源分攤；正式條款需法律審閱。
6. 錢包 API／物理 SQL schema、資料保留／刪除界線、雙人覆核範圍、對帳頻率、備份與事故處理。
7. 未來是否選配信用卡或第三方支付；若採用，供應商資格、費率、退款／爭議、未知結果、tokenization 與正式 credentials。

先完成上述商業及法定決策，再展開 API／schema／遷移計畫與安全 Profile，通過 Gate 1 規劃審批及 Gate 2 實作準備審批後才實作。工時、供應商成本與上線日期暫不估算，因入金路徑、法規與帳本對帳作業未定；依正式入金與退款規則決策後提供粗估與信心範圍。
